# Realtime collaboration options for Ideate

**Accessed:** 2026-09-13  
**Question:** What should Ideate use to add multiplayer collaboration across its Excalidraw board, CodeMirror code and notes, presence, persistence, and files?

## Executive answer

Use **Liveblocks for the first production implementation**, with one room per Ideate workspace. Use Liveblocks-hosted Yjs for code and notes, Presence for pointers, selections, identity, and active-tool state, and a deliberate Excalidraw adapter for the board. This gives the project managed WebSockets, persisted Yjs updates, room permissions, presence, and file storage without first operating a stateful collaboration service. Liveblocks publishes an official [CodeMirror + Yjs + Next.js guide](https://liveblocks.io/docs/guides/how-to-create-a-collaborative-code-editor-with-codemirror-yjs-nextjs-and-liveblocks) using `y-codemirror.next`.

Choose **Yjs with Hocuspocus** instead when self-hosting or control of persistence is a firm requirement. CodeMirror 6 has a stable official [`y-codemirror.next`](https://github.com/yjs/y-codemirror.next) binding, and the same Yjs document model can move between providers, but Excalidraw still needs an app-owned adapter. Hocuspocus supplies a practical authenticated WebSocket server around Yjs, while Ideate must operate persistence, scaling, monitoring, backups, and object storage.

Do not build the whole workspace directly on custom Socket.IO for the first release. Excalidraw's own example server is useful reference code, but it is only the transport layer. Ideate would still have to implement durable rooms, authorization, reconnection snapshots, board conflict behavior, text concurrency, file storage, and production operations.

## The Excalidraw boundary

Installing `@excalidraw/excalidraw` does **not** give the host application a hosted collaboration backend. The package exposes the editing surface and integration hooks: [`onChange`, `onPointerUpdate`, and `isCollaborating`](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/), plus imperative APIs including [`updateScene`, `addFiles`, `getFiles`, and `getSceneElementsIncludingDeleted`](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/excalidraw-api). The upstream Excalidraw app separately configures a [collaboration WebSocket server and Firebase storage](https://github.com/excalidraw/excalidraw/blob/master/.env.production), and its Socket.IO server lives in the separate [`excalidraw-room`](https://github.com/excalidraw/excalidraw-room) repository. The `LiveCollaborationTrigger` is a UI callback, not a service.

The adapter must publish element changes, receive remote changes, and apply them through `updateScene` with `CaptureUpdateAction.NEVER`, which Excalidraw documents for [remote updates that must stay out of local undo](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/excalidraw-api#captureupdate). It should retain deleted elements as tombstones. Excalidraw's element schema includes [`version`, `versionNonce`, fractional `index`, and `isDeleted`](https://github.com/excalidraw/excalidraw/blob/master/packages/element/src/types.ts); removing a tombstone too early can allow an older live copy to reappear.

Choose one board winner policy and make it authoritative. The simpler first-release policy is a server-ordered last writer per element ID in Liveblocks Storage, with tombstones retained and Excalidraw's version fields treated as payload metadata. The closer-to-upstream policy is an update stream reduced with public [`reconcileElements`](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/data/reconcile.ts), whose winner rules use `version`, `versionNonce`, local editing state, and fractional ordering. Do not layer a `LiveMap`/`Y.Map` last-writer winner over Excalidraw reconciliation and assume they are equivalent: concurrent edits to the same element can choose different winners. Spike and test same-element move/resize/delete conflicts before fixing the board schema.

Pointers and collaborators are ephemeral. Capture board coordinates from `onPointerUpdate`, broadcast a small presence record, convert current peers to Excalidraw's collaborators map, and pass it through `updateScene`. Do not persist cursor traffic. Both [Liveblocks Presence](https://liveblocks.io/docs/products/sync/presence) and [Yjs Awareness](https://docs.yjs.dev/getting-started/adding-awareness) are designed for this and remove a user's state when the connection ends.

Images are a second data plane. Excalidraw elements carry `fileId` references while the bytes are read and inserted separately through `getFiles`/`addFiles`. Upload bytes once under a content/file ID, store only the reference in collaborative document state, fetch missing assets on demand, and preserve old assets while undo/history can still refer to them. Liveblocks' [`LiveFile`](https://liveblocks.io/docs/products/sync/storage) keeps file bytes outside realtime Storage and returns presigned URLs. A self-hosted design needs equivalent S3-compatible object storage and authorization; the Yjs document should not carry base64 image blobs.

## Options compared

| Option | What it supplies | What Ideate still owns | Hosting and cost shape |
| --- | --- | --- | --- |
| **Liveblocks-hosted Yjs + Storage** | A managed room, persisted `Y.Doc`, Yjs Awareness through [`@liveblocks/yjs`](https://liveblocks.io/docs/api-reference/liveblocks-yjs), Presence, permissions, Storage, and file support. | The Excalidraw adapter and canonical winner policy, lifecycle/history across Yjs and Storage, product access rules, and IndexedDB migration. | Managed and [usage-metered](https://liveblocks.io/docs/pricing/plans) across collaboration time, updates, storage, and files. A free tier suits prototypes; spend grows with active collaboration and stored activity. [Self-hosted Sync is an Enterprise add-on](https://liveblocks.io/docs/platform/data-storage). |
| **Liveblocks Storage + LiveText** | Managed persistent records and LiveText, Presence, permissions, versions, and a first-party [`@liveblocks/codemirror`](https://liveblocks.io/docs/api-reference/liveblocks-codemirror) adapter. | The same board adapter; a later move away from Liveblocks also requires changing the text model and editor binding. | The same managed cost shape. This is a valid alternative if one vendor-specific Storage/history model matters more than Yjs portability. |
| **Yjs + Hocuspocus** | CRDT shared types, Awareness, offline/browser persistence options, and a self-hosted WebSocket provider. Hocuspocus adds token-based connection auth and server hooks. | Deployment, TLS, availability, upgrades, observability, backup/restore, tenancy, database and blob storage, abuse controls, and Excalidraw mapping. | Open-source software shifts cost toward compute and operations. Small deployments can be inexpensive, but production cost expands to the WebSocket service, database, backups, object storage, and usually Redis when scaling horizontally. |
| **Custom Socket.IO / `excalidraw-room`** | A direct event transport closely resembling the upstream Excalidraw app. | Nearly every product guarantee: authoritative snapshots, catch-up/reconnect, persistence, membership/auth, text merge semantics, presence expiry, file transport, scaling, and disaster recovery. | Low initial infrastructure cost and no collaboration vendor fee, with the highest engineering and operational cost. |

Liveblocks and Yjs are not mutually exclusive: Liveblocks can host Yjs. For Ideate, hosted Yjs fits the existing CodeMirror 6 editors and keeps Hocuspocus as a plausible later provider. Liveblocks explains that a [Yjs document in a room remains separate from Storage](https://liveblocks.io/docs/guides/livetext-vs-yjs), with its own lifecycle, API, and binary format. If the board uses Storage while text uses Yjs, atomic whole-workspace versions and undo do not come for free; Ideate must define that product behavior.

## The self-hosted Yjs path

Yjs provides shared types and deterministic merging, not an all-in-one hosted product. Its [collaborative editor guide](https://docs.yjs.dev/getting-started/a-collaborative-editor) explicitly separates editor bindings from network providers. For Ideate, bind each CodeMirror document to a `Y.Text` with `yCollab(yText, provider.awareness, { undoManager })`. The binding syncs CodeMirror 6, renders remote ranges/cursors, and supports a Yjs undo manager whose history is local to each client.

For local resilience, [`y-indexeddb`](https://docs.yjs.dev/ecosystem/database-provider/y-indexeddb) reloads document updates from IndexedDB and permits offline editing. For a central server, the basic [`y-websocket`](https://docs.yjs.dev/ecosystem/connection-provider/y-websocket) provider exchanges document updates and Awareness, supports cookies/headers for existing auth, and can use LevelDB persistence, but its scaling section is guidance rather than an operated platform.

Hocuspocus is the more complete self-host baseline. Its [`onAuthenticate`](https://tiptap.dev/docs/hocuspocus/guides/authentication) hook can reject a token or mark a connection read-only. Its generic [database extension](https://tiptap.dev/docs/hocuspocus/server/extensions/database) loads and stores Yjs-compatible binary state in PostgreSQL, MySQL, MongoDB, S3, or another store. Its [Redis extension](https://tiptap.dev/docs/hocuspocus/server/extensions/redis) synchronizes documents and awareness across instances, but explicitly does not persist them, so a database remains necessary.

[PartyServer/Y-PartyServer](https://github.com/cloudflare/partykit) is a credible Cloudflare Workers/Durable Objects variant: its official repository provides Yjs synchronization plus hooks for loading and saving documents to external storage. The same repository labels the current project a work in progress, so prefer Hocuspocus for a conventional self-hosted service today unless Cloudflare Durable Objects are already a deployment constraint.

## Recommended first slice

Create a private Liveblocks room only after the app's server verifies the signed-in user. Liveblocks recommends server-issued ID tokens for production and supports default, group, and user room permissions, including separate [`storage:read` and `storage:write`](https://liveblocks.io/docs/authentication/permissions) scopes.

Start with code and notes as separate `Y.Text` values bound through `y-codemirror.next`, then spike the two board policies above before choosing one. Presence should contain user identity, active tool, board pointer, and text selection. Keep `isDeleted: true` records until a compaction policy accounts for retained snapshots and clients that may reconnect with older state. Store Excalidraw files through LiveFile or an object store.

This requires a state-model migration, not a socket bolted onto the current callbacks. Ideate currently replaces each CodeMirror value as a full string, replaces the whole board array on every Excalidraw change, and persists the entire workspace under one IndexedDB key. Make the collaborative document the shared source of truth and keep Zustand as a local UI projection. Scope any local cache by room/document ID, and ensure remote board applications never enter Excalidraw's local undo stack.

The AI/voice path needs a collaboration contract too. Numeric revisions incremented independently on two clients are not a safe concurrency guard. Validate proposals against the exact relevant content or a deletion-aware snapshot/version, elect one executor for each accepted operation, and attach an operation ID so retries apply once. The current voice presentation animates transient local previews before a final commit; peers will see the committed result unless preview events are explicitly modeled as ephemeral presence.

This slice delivers visible co-editing without changing the Python runner's isolation or making AI operations silently authoritative. It also leaves an exit path: the Excalidraw adapter and board policy remain app-owned, while the Yjs text layer can move to Hocuspocus later if self-hosting becomes a real requirement.
