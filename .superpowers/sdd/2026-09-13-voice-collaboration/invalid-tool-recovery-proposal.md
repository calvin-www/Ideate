# Bounded invalid-tool recovery proposal

Read-only design investigation of `src/features/ai/server/handler.ts`, `provider.ts`, `budget.ts`, `validation.ts`, `tests/ai-recovery.test.ts`, `tests/ai-server-stream.test.ts`, and `tests/ai-budget-integration.test.ts`. Root owns reproducing the drawing schema rejection and tool diagnostics; no implementation files changed here.

## Existing behavior

The handler buffers all provider parts and tool calls, while streaming ordinary visible text. It requires STOP before validating/issuing calls. `validatedCalls = calls.map(...)` validates the entire batch before its later emit loop, so one invalid call already prevents every call from being emitted. Today a schema rejection throws immediately with a generic invalid-operation error. There is no model repair opportunity.

The handler already has the right recovery machinery: one 55-second abort/deadline signal, pre-reserved generation allowance, completed STOP usage refunds, cumulative response-byte limits, a shared job recovery count (default two), iterator cleanup, and signed single-use continuation budgets. MAX_TOKENS uses this loop; initial transient 503 uses the same budget/recovery count. Preserve those boundaries.

## Recommended algorithm

1. Only consider automatic schema repair after a completed STOP whose batch remains within the 12-call hard cap and response/continuation size limits. Missing completion, SAFETY/blocked generation, network failure after streamed output, and response resource limits retain existing failure handling.
2. Diagnose every call first using the root's bounded diagnostic helper. Keep the successful parsed arguments separate from the untouched provider `Part[]`. Treat unsupported call names/envelopes and duplicate provider call IDs as whole-batch failures too. Emit no calls and issue no tool checkpoint for a failed batch.
3. Roll visible text back to `beforeAttempt` with the existing replace event, then restore `visibleText = beforeAttempt`. This removes claims from the failed generation while preserving prior successful partial text and all earlier applied operations.
4. Create repair context according to whether the failed turn can be faithfully replayed:
   - For a known tool with a valid optional ID and object arguments, preserve the entire original model parts unchanged (including thought signatures, thought parts, raw argument fields, ordering, and IDs). Follow with a user content containing exactly one functionResponse per original call. Invalid calls receive `{output:{status:'invalid_arguments',message:'No operation in this batch was executed.',issues:[...]}}`; valid sibling calls receive `{output:{status:'not_executed',message:'Another operation in this batch was invalid. No operation in this batch was executed.'}}`. Match function name and preserve a provider ID when present; do not invent IDs inside signed provider content. Feedback tells Gemini to regenerate a small complete batch using exact current revisions or read current data first, without claiming anything was applied.
   - For unknown/missing names, malformed IDs/argument envelopes, duplicate IDs, or other provider parts that cannot pass the existing continuation envelope, discard the entire failed attempt. Keep all prior accepted contents untouched and append a bounded plain-text regeneration instruction with controlled diagnostic facts. This is the same whole-attempt discard principle as truncated-tool recovery. Do not rename calls, overwrite arguments, remove individual signed parts, or smuggle unknown tool names through browser validation.
5. Apply `checkContinuation` to the candidate repair context before generating. Keep the same immutable messages/context fingerprint. Do not reset cumulative outputBytes. Default maximum extra feedback should be a few KiB (e.g. at most 3 issues per call, 12 calls, each issue path/message bounded), without echoing code, document text, raw unknown values, or secrets.
6. Retry only if `budget.remaining > 0`, `budget.recovered < budget.recoveries`, and the shared signal is live. Increment `recovered`, emit a short status such as 'Correcting the proposed operation...', close the prior iterator, and invoke `openGeneration(true)` against the repair contents. Do not start a new deadline, new budget, new rate-limit admission, or new tool round. The additional generation uses the same reservation/refund accounting as all other attempts.
7. If schema repair exhausts its allowance/recovery cap, emit a controlled final error with the affected operation and short reason when safely available, retaining the existing no-call/no-done terminal contract for invalid operations. This preserves the current invalid-write test and avoids issuing a resume checkpoint containing an unreplayable malformed turn. Previously completed workspace changes remain intact. A separately chosen pause-at-budget policy is possible, but must checkpoint valid repair context, preserve append semantics, and be covered explicitly; it is not necessary for this bounded fix.
8. On success, execute the existing all-calls-validated emission and tool-token path unchanged. The browser remains the only operation executor: exact revisions, approval/auto-apply, operation deduplication, presentation, and execution authorization are unaffected. Synthetic repair responses describe nonexecution only; they do not pretend to read artifacts or approve edits.

`provider.ts` currently uses recovery=true to append 'The last generation reached its output limit'. Validation repairs should not get a false diagnostic. Prefer a reason-neutral recovery suffix ('Keep this recovery concise; return a small complete operation and follow any validation feedback'), preserving GenerateStream's current boolean signature. A reason enum is possible but unnecessary interface churn for this fix.

## Tests with highest value

1. **Repair succeeds:** STOP with invalid nested teach_step/edit_board arguments, then a valid corrected call. Assert two generations, one emitted valid call, one done event, a correction status, and no generic error. Inspect second generation input for bounded actual issue paths.
2. **Whole-batch atomicity:** first attempt contains a valid edit_notes and invalid edit_board. Assert neither original call is emitted or executed. Model gets one not_executed/invalid_arguments response per original call. Corrected batch can subsequently be emitted once.
3. **Signed-turn preservation:** attach distinct opaque thoughtSignature fields to first/multiple provider parts, with explicit call IDs and one missing ID. Assert original repair-context model parts deep-equal originals, function responses match names/available IDs, and repaired continuation survives parseAiRequest/buildContents on the next request. No repair mutates raw model arguments in place.
4. **Malformed envelope fallback:** unknown tool, malformed/missing name, oversized or duplicate provider IDs, nonobject arguments. Assert bounded regeneration context contains no malformed failed model turn and successful repaired continuation is accepted on its next browser round. No invalid calls escape.
5. **Rollback:** fail after streamed text following an earlier MAX_TOKENS partial-text recovery. Only the invalid attempt's text is replaced; previous text survives, corrected text appears once, prior applied edits remain unchanged.
6. **Shared recovery cap:** repeatedly invalid STOP with valid low usage and a large token budget makes exactly three total generations (original plus two shared recoveries), then a safe error and no call/done. Mixed MAX_TOKENS then invalid STOP consumes the same two-recovery pool. A corrected tool continuation must retain used recovery count and cannot get fresh retries.
7. **Token accounting:** invalid STOP with missing usage charges its full reservation; valid STOP usage includes thoughts in its charge even though call arguments were invalid. No retry if remaining is zero, and no allowance exceeds remaining. Keep existing replay/tamper/expiry checkpoint tests unchanged.
8. **Cancel/deadline/limits:** abort between invalid STOP and retry, during correction generation, and after status emission; no late calls/done and no subsequent provider request. Keep safety/no-completion/too-many-tools/too-large-response nonrecoverable. Cumulative output and continuation bounds include all repair attempts.
9. **Client execution integration:** corrected proposal in review mode still waits for approval; auto-apply commits only the corrected batch once; manual edit during repair still causes normal exact-revision rejection at the browser executor. A failed invalid run request does not grant Python execution permission during repair.

## Risks and decisions

- Replaying malformed tool names/envelopes can poison the next browser continuation even if the immediate repair succeeds, because `partSchema` only accepts known tool names, valid IDs, and object arguments. Keep failed complete turns only when round-trippable; otherwise discard whole turn.
- Never 'repair' by coercing baseRevision, dropping unsupported mutations, clamping geometry, or automatically accepting a proposal. Feedback lets the model regenerate; current validation remains authoritative.
- A valid sibling may be an edit or run. Its synthetic response must explicitly say it was not executed, and all calls must be blocked before the first emission.
- The default two recoveries are shared across the whole job. A long job may reach an invalid call with no recoveries remaining; fail clearly rather than silently expanding limits.
- Two failed attempts add model/response content and can approach the existing 32-content/4-MiB continuation ceiling. Check it before recovery and checkpoint issuance.
- Schema validation and proposal validation are different. This server repair addresses structurally invalid model calls; current artifact conflicts, unsupported board relationships, manual edits, and user rejection continue through normal browser operation results.

## Implemented and verified

Implemented the proposal in `src/features/ai/server/handler.ts` and made the recovery suffix reason-neutral in `provider.ts`. Added `tests/ai-tool-recovery.test.ts` with 12 cases, including an actual handler-to-collaborator review/manual-revision integration. Root supplied the bounded `toolValidationIssues` helper and owns drawing-schema/arrow geometry changes.

The first focused run demonstrated 10 failing cases against the old behavior (no schema repair); the preexisting cancellation case passed. After implementation and the diagnostics export, all 40 tests passed across `ai-tool-recovery`, `ai-recovery`, `ai-server-stream`, `ai-budget-integration`, and `ai-client-recovery`. `npx tsc --noEmit` also passed. No commits were created.

Decisions: schema exhaustion ends with a controlled error rather than a paused checkpoint; unknown/malformed/duplicate envelopes regenerate from prior valid contents plus generic bounded guidance. Known invalid argument batches retain original signed parts and matched nonexecution responses. All retries share token budget, recovery count, deadline, output-byte cap, and cancellation signal. Successful repaired calls still use the existing browser approval and revision validation path.
